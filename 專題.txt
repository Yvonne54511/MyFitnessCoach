📦 專案名稱：營養師預約管理後台系統
角色定義：

營養師 (Provider)： 提供諮詢服務、管理個人排班與訂單者。

系統管理員 (Admin)： 維護平台秩序、處理爭議與系統設定者。

客戶 (User)： 前台預約服務的消費者（此份文件聚焦後台，故以營養師視角為主）。

模組一：排班與時段管理 (Availability Management)
📝 User Story (使用者故事)

「身為一位營養師，我希望能在系統後台以月曆介面，透過勾選『週、日、時段（早/中/晚）』的方式
開放我的可預約時間，以便讓客戶能在前台看到並進行預約。」

✅ Acceptance Criteria (驗證準則 - AC)

介面顯示： 系統需以「月」為單位顯示日曆，並明確標示當月開放與未開放的時段。

新增/開放時段： 營養師勾選特定時段（早/中/晚）並儲存後，該時段狀態更新為「開放預約 (Available)」。

取消/關閉時段： * 營養師可取消已勾選的時段。

[防呆機制] 若該時段已有客戶預約並成立訂單，系統需跳出阻擋提示：
「此時段已有客戶預約，無法直接關閉，請至訂單管理進行取消操作。」


[防呆機制與次數限制] 每個營養師每個月有三次更改時段的次數，若時段判定送出資訊相同，
則不會扣減次數；每次修改後，次數-1；次數為0時，無法再次送出請求(按鈕設為disabled) 
**系統仍會判定次數是否為0，阻擋更改前端的有心人士**
*商業邏輯:每個月首次送出紀錄，不會扣減次數

*使用ILogger，追蹤業務邏輯流向*: 透過內建日誌追蹤登入的該營養師剩餘修改班表次數

Admin能查看所有營養師排班，並能夠透過營養師、排班時間、預約狀態去篩選


模組二：預約紀錄與訂單管理 (Order & Booking Management)
📝 User Story (使用者故事)

「身為一位營養師，我希望能完整查詢客戶的預約訂單，並能增加、修改備註內容
，以便我掌握每月的實際諮詢排程與收入狀態。」

✅ Acceptance Criteria (驗證準則 - AC)

訂單查詢： 可依據「日期區間」篩選並查看預約紀錄。

紀錄會隨著admin修改預約狀態而消失或顯示

點擊詳細資訊，可以查看被隱藏的顧客期望，也可以新增或修改備註內容(字數限制100，超過時會無法輸入)

修改備忘錄限制(五日後設為唯讀)


模組三：客戶評價管理 (Review Management)
📝 User Story (使用者故事)

「身為一位營養師，我希望能查看客戶在諮詢後給予的評分與評論，以便我了解服務滿意度並進行優化
，針對不合適言詞，我希望能夠有管道進行申訴。」

✅ Acceptance Criteria (驗證準則 - AC)

評價檢視： 營養師可在後台列表查看所有關於自己的歷史評價。

評論舉報處理：營養師能透過舉報評論傳通知給admin。

extra:

系統內建敏感詞存放庫，若客戶留言包含敏感字眼，系統自動將該字詞以「***」模糊化處理。

admin可以對敏感詞庫做增刪改

評論的敏感字詞可被解除模糊化

模組四：通知 (Notification)
📝 User Story (使用者故事)

「身為系統使用者（營養師、系統管理員 Admin、客戶），我希望能即時收到與我相關的系統動作通知
（如：收到新預約、預約遭取消、排班異動警告、評價回報審核等），以便我能掌握最新動態
，而系統端也能用最輕量的方式處理訊息種類。」

✅ Acceptance Criteria (驗證準則 - AC)

動作觸發機制： 結合前三個模組的事件，當特定行為發生時（如：客戶送出預約、Admin 取消預約、營養師回報評價）
，系統會自動觸發通知發送流程。

輕量化與低耦合設計： 系統不建立額外的「訊息種類 (Message Category)」資料表與關聯。
訊息種類一律由系統後端程式碼中的 Enum 統一定義，降低資料庫 Join 的負擔。

動態訊息生成： 透過 switch 判斷 Enum 的值，將變數（如：訂單編號、營養師姓名、日期）動態嵌入字串中
，生成最終的通知標題與內容。

角色分流： 系統能依照動作類型，將通知精準派發給對應的 UserID（例如：評價回報通知僅發送給 Admin
，新預約成立則發送給營養師與客戶）。


模組五：數據統計與評價分析看板 (Dashboard & Keyword Analytics)
📝 User Story (使用者故事)「身為系統管理員 (Admin)，我希望能透過 Dashboard 儀表板
查看營養師的綜合評分比較，並藉由系統的關鍵字加權模型自動判定評論的正負向情緒
，以便客觀掌握服務品質與績效獎金核發；同時，我希望能快速找出高頻出現的未分類詞彙，將其新增至關鍵字庫中。」

✅ Acceptance Criteria (驗證準則 - AC)混合模型評分機制： 系統需針對每則評論計算最終情緒分數
判定流程分為三階段：
	Step 1. 基礎分設定： 
		1–2 星為 -2 分
		3 星為 0 分
		4–5 星為 +2 分

	Step 2. 關鍵字加權： 掃描留言內容，出現負面詞則 -1 * 權重分，出現正面詞則 +1 * 權重分
	
	Step 3. 最終判定：星星基礎分 + 關鍵字*加權
	（判定標準：> 0 為正評；= 0 為中立/待觀察；< 0 為負評）

防呆機制與權重覆蓋： 
若評論中出現重疊或包含關係的字串（例如：Id=2「絕對推薦」與 Id=10「推薦」）
，演算法需自動選擇字串較長或權重較高的關鍵字進行計算，避免重複加分導致失準。

動態未分類詞彙抓取： 
於關鍵詞明細 Dashboard 中，系統需動態運算並列出「未分類字詞」
判定條件：
	使用N-Gram（連續詞彙）的高頻詞頻率分析功能
	文字探勘（Text Mining）跟自然語言處理（NLP）
	字詞出現次數 > 5 次，且為 2-5 字組成。
系統限制：此清單不寫入實體資料庫，僅由後台動態運算並顯示於前端看板。

關鍵字擴充： Admin 可直接於 Dashboard 點擊「未分類字詞」，將其編輯並新增為系統正式的關鍵字庫（Keywords）


模組六：違規會員與評論管理 (Violation & Suspension Management)

📝 User Story (使用者故事)「身為系統管理員 (Admin)，我希望能有完善的違規處理機制
，針對惡意攻擊的評論進行隱藏、並對違規會員發出警告與實施停權，以便維護平台良好的預約與互動環境。」

✅ Acceptance Criteria (驗證準則 - AC)異常評價與狀態標記： 
若 Admin 判定某則評論為惡意攻擊，可操作按鈕將該評論標記為「封鎖留言」（前台不顯示），或將該會員狀態更改為「停權」（會員停權後將無法進行預約）

評分儀表板連動： 若某則評論狀態被設為「封鎖留言」，該則評論的分數與內容將不會被計入「模組五」的營養師評分統計 Dashboard 中

警告次數與自動提醒機制： * 當 Admin 針對某會員點擊「封鎖留言」時，系統將自動使該會員的「警告次數 +1」

當該會員警告次數達到或超過 5 次時，系統需跳出明顯提示，強烈建議 Admin 停權該會員

定期重置機制： 系統需設定排程，每兩個月自動刷新並清空所有會員的違規管理紀錄與警告次數。

模組七：薪資核發與財務管理 (Payroll & Financial Management)
📝 User Story (使用者故事)
「身為系統管理員 (Admin) 與營養師，我希望能透過系統自動計算績效獎金
，並能串接第三方金流、匯出帳務報表，以便透明、準確地管理與追蹤薪資發放紀錄。」

✅ Acceptance Criteria (驗證準則 - AC)

績效獎金計算 (Weighted Scoring System)： 
系統需實作綜合權重積分法，分為「月」與「年」兩種結算模式。計算公式如下：

月結算積分：
	Total Score = (Booking Count*0.5) + (Average Rating*0.3) + (Positive Review Count*0.4)

年結算積分：
	Total Score = (Booking Count*0.3) + (Average Rating*0.4) + (Positive Review Count*0.5)
為了讓營養師維持高品質的服務，而不是一昧的重量不重質

獎金分配公式：
	(個人 Total Score / 全體 Total Score) × 獎金池金額


發放門檻與彈性設定：

月預約次數未滿 15 次，或年預約次數未滿 100 次者，不予計分。

系統管理員可於後台動態調整「獎金池金額」。
